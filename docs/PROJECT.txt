NEON STACK + LOGFIRE

Purpose
Connect Apple performance evidence to its app build and game session.
Keep Xcode build, run, debug, and profile workflows familiar.
Status: experimental integration for trusted developer and manual tester builds.
Toolchain: Xcode 27 with its Metal toolchain. Native lookback requires macOS 27.

Setup
Open examples/neon-stack/NeonStack.xcodeproj.
Configure a write token once with swift run logfire-apple configure --region us.
Existing private prototype credentials remain compatible.
Select NeonStack and My Mac. Press Cmd-R. LLDB remains enabled.
The SDK and ordinary build identity step require no Python or relay.
Run swift run logfire-apple doctor to inspect setup without displaying credentials.

Data flow
Game operation -> Swift SDK -> OTLP HTTPS -> Logfire.
Renderer frame samples -> SDK FrameRecorder -> five-second windows -> Logfire.
Rendering context -> SDK state API -> Logfire and Apple StateReporting.
Apple MetricKit reports -> adapter inside the SDK -> historical Logfire spans.
Apple display/resource measurements -> optional Swift companion -> Logfire.
Native capture -> local recording, symbols, checksums, and Logfire metadata.
Host Swift build step -> embedded build identity -> app startup identity record.
Optional Python build observer -> complete build trace and build-time host samples.

Native evidence
Keep the game running. From the repository root, run:
swift run logfire-apple capture --last 10s
For live measurements, run:
swift run logfire-apple attach --seconds 30
Use --service neon-stack when multiple instrumented apps run.
Add --no-telemetry to keep evidence local.
The companion verifies the process, executable, process start time, and embedded build ID.
It selects the latest live SDK session automatically.
Open the retained .atrc recording in Instruments.
The manifest identifies the session, build, measurement interval, binary, symbols, and artifact checksums.
The recording can contain other processes. Exported summaries select our PID.

Optional build investigation
Run uv sync --frozen --project tools/xcode-observe only for advanced host workflows.
Use swift run logfire-apple build with observer options and xcodebuild arguments.
Full build timing still uses the Python observer. It is an optional companion action.
Controlled seeded replays and relay comparisons also remain available in that package.
Import dashboard JSON from tools/xcode-observe into your Logfire project.

Terminology
SDK: native Swift application integration, distributed as a Swift package.
FrameRecorder: reusable sampler and window exporter inside the SDK.
Context: mode, resolution, workload, detail, thermal state, and build/session identity.
Span: a timed operation or an explicitly timestamped measurement window.
OTLP: the OpenTelemetry export protocol.
Signpost: native event or interval on an Instruments timeline.
StateReporting: Apple state context for profiling tools and MetricKit.
MetricKit: Apple metric and diagnostic report delivery to the application.
Adapter: code inside the SDK that selects Apple report fields and exports them.
Companion: optional Swift host command for capture, live attach, and build-tool routing.
Relay: optional host forwarder for transport comparisons. Direct SDK export needs no relay.
metalperftrace: Apple's macOS CLI for live and historical Metal measurements.
Capture: Apple recording artifact, distinct from an OpenTelemetry trace.
Build ID: identifies the app build and joins its runtime records and captures.
Session ID: identifies one app run and joins independent operation and measurement records.
Source digest: fingerprints source, package inputs, and project settings.
dSYM: retained debug symbols for native analysis.

Measurement limits
Callback FPS differs from presented FPS. Preparation wall time differs from CPU utilization.
GPU command duration is not hardware utilization.
Native CPU times are not CPU utilization percentages.
Compare matched Release devices, modes, sizes, seeds, and workloads.
Do not average window percentiles into a session percentile.
Performance windows and Apple reports currently use span attributes, not OTel metric instruments.
MetricKit preserves historical dates and reported versions. It omits current-session build and session IDs.
Full-day and state reports can overlap. The adapter does not deduplicate reports.
Diagnostic summaries omit raw exception messages and backtraces.
Neither transport has a durable queue. Failed batches and abrupt stops can leave gaps.
Delivery counters describe attempted batches. They cannot count every lost record.
Capture currently requires a live verified SDK session. Finished-session capture remains future work.
Physical iOS runtime, real MetricKit delivery, and a second tester Mac remain unverified.
